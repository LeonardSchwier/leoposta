# i18n (en + de) — design

Date: 2026-11-07 (rev 2 post builder-check)
Owner: Leonard
Status: proposed (pending approval)

## Intent and why

`ROADMAP.md` P2 item: *"i18n (start en, add de/es/fr)."* Today every UI
string in `src/**/*.svelte` is hard-coded English. Users outside
en-locale apps read an English mail client (including German, which is
the natural market for this project). This change gives the user a
working language switch in Settings and produces German translations
for every visible string in the UI. Future es/fr work reuses the same
mechanism.

## Goals

- Every user-facing English string — button labels, headings,
  placeholders, `title`/`aria-label`, empty states, built-in folder
  labels, rule field/operator/action labels — renders in the active
  language.
- Language selectable in **Settings** (new **Language** tab, per
  Leonard's 2026-11-07 call). Radios, immediate effect, no save button.
- Defaults to the user's OS preference when `navigator.language`
  starts with `de` (any German tag — `de-DE`, `de-AT`, `de-CH`,
  `de-LU`, …); otherwise falls back to `en`.
- Choice persists in `localStorage('leoposta.lang')` across sessions;
  cross-tab changes propagate via the `storage` event.
- No flash-of-wrong-language on first paint (synchronous load from
  `localStorage`, fallback `navigator.language`, fallback `en`).
- On language change, update `<html lang>` for screen readers /
  spellcheckers / IME.

## Non-goals (anti-goals)

- No third-party i18n library (see Approaches below).
- No runtime locale negotiation with the server. The server stays
  English (API errors, server logs) — the UI translates the wrapper
  text and leaves the raw `err.message` / `data.error` body verbatim.
- No full ICU plural rules. We need only the **1 / other** split
  (en and de both use that), handled by a tiny `tPl(key, n)` helper
  with `{n}` + `{one}`/`{other}` slots. If we add es (1 / few / many /
  other) or sl (1 / few / many), we swap to `svelte-i18n` then.
- No PWA-manifest translation (static file; document the limitation).
- No runtime translation of server-defined IMAP folder names (they
  stay as the server returns them). Built-in client-side folder labels
  (Inbox, Sent, Drafts, Trash, Archive, Flagged) ARE translated.
- No tests for German translation accuracy (a QA job). We test the
  plumbing: fallback, params, plurals, persistence, cross-tab,
  reactive re-render.

## Constraints

- Works offline (PWA) — locale files are bundled at build time.
- Svelte 5 runes (`$state` / `$derived`) matching existing style.
  `t()` must be reactive when the language changes mid-session.
- Must pass existing gates unchanged: `npx vitest run` (66 tests),
  `node --test server`, `npx tsc --noEmit`, `npx vite build`.

## Approaches considered

| Approach | Pro | Con | Verdict |
|---|---|---|---|
| **A. Hand-rolled `t()` + rune-based store** | Zero new deps; ~80 lines of code; fits the repo's runes style; trivial to swap later | No ICU plurals out of the box (we ship 1/other, which en/de need) | **Pick** |
| B. `svelte-i18n` + `vite-plugin-svelte-i18n` | Mature, typed, ICU plural, `browser()` / `storage()` helpers | Two new npm deps + a Vite plugin; overkill while we're bilingual | Defer until es/fr lands |
| C. i18next / react-i18next | Industry standard, huge ecosystem | Not Svelte, heavier dep tree, same over-kill | Rejected |

Chosen: **A**.

## Design

### New module: `src/lib/i18n.ts`

```ts
export type Lang = 'en' | 'de'

// dicts.ts exports `en` and `de` as `Record<string, string>` (flat).
// keys.ts exports `type LocaleKey = keyof typeof en`.

let lang: Lang = $state<Lang>(initialLang())

export function setLang(next: Lang) {
  if (!(next in dicts)) return
  lang = next
  try { localStorage.setItem('leoposta.lang', next) } catch { /* private mode */ }
  try { document.documentElement.lang = next } catch { /* SSR (n/a here) */ }
}

// Strict key: typos are compile errors. New strings must be added
// to BOTH `en` and `de` before use (or to `en` first — the runtime
// fallback below covers the de-missing case).
export function t(key: LocaleKey, params?: Record<string, string | number>): string

// Plural: `tPl(key, n)` → `t` with slots {n} + {one} + {other}
// filled from the active dict. en/de only need 1/other.
export function tPl(key: LocaleKey, n: number): string

function initialLang(): Lang {
  try {
    const stored = localStorage.getItem('leoposta.lang')
    if (stored === 'en' || stored === 'de') return stored
  } catch { /* localStorage unavailable */ }
  const nav = (typeof navigator !== 'undefined' && navigator.language) || ''
  if (nav.toLowerCase().startsWith('de')) return 'de'
  return 'en'
}
```

Notes:

- **Reactivity.** `lang` is a rune; a component that calls `t()`
  inside `$derived` or inside the template re-renders when
  `setLang()` runs. Calling `t()` inside an event handler sees the
  call-time language (correct, matches user intent).
- **Fallback semantics.** `t()` = `dicts[lang][key] ?? dicts.en[key] ?? key`.
  A missing `de` entry transparently falls back to `en`, so partial
  de translations don't break the UI.
- **Missing-in-both.** Returns `key` verbatim. Logs a single
  `console.warn` per unique key (dedupe with a `Set<LocaleKey>`) to
  avoid spam on hot paths.
- **Param substitution.** `{name}` syntax, via `replace(/\{(\w+)\}/g,
  …)` two-pass. If a substituted value contains `{`/`}`, it does not
  trigger a second pass (accepted edge case — we never pass
  user-typed values into `t()` params for translation; we pass them
  only as opaque suffixes like `{ err }` where curly braces are not
  expected).
- **Cross-tab.** On module load, register
  `window.addEventListener('storage', handler)` that updates `lang` if
  `event.key === 'leoposta.lang'` and the value is valid `en`/`de`.

### Locale files

- `src/lib/locales/en.ts` and `src/lib/locales/de.ts` — each exports
  a flat `Record<LocaleKey, string>` (or `Record<string, string>`
  if we don't want the strict export; see next).
- `src/lib/locales/keys.ts` — `export type LocaleKey = keyof typeof en`.
- Key naming: `<component>.<context>.<field>`, e.g.
  `settings.tab.language`, `compose.to.placeholder`,
  `rules.field.subject.label`, `app.send.success` (with `tPl`).
- New strings found during rollout get added to **both** `en` and
  `de` dicts (or to `en` first if `de` will be added later — but
  the key MUST exist in `en`, otherwise we hit the missing-in-both
  path).

### Settings — new Language tab

`activeTab` union gains `'language'`:

```ts
let activeTab = $state<'account' | 'rules' | 'language'>('account')
```

Initial tab stays `'account'` (least surprise).

New tab button + radio body:

```svelte
<button class={activeTab === 'language' ? 'tab active' : 'tab'}
        onclick={() => activeTab = 'language'}>
  {t('settings.tab.language')}
</button>
<!-- … -->
{#if activeTab === 'language'}
  <h3>{t('settings.language.heading')}</h3>
  <label class="lang-opt">
    <input type="radio" name="leoposta-lang"
           checked={lang === 'en'}
           onchange={() => setLang('en')} />
    {t('settings.language.option.en')}
  </label>
  <label class="lang-opt">
    <input type="radio" name="leoposta-lang"
           checked={lang === 'de'}
           onchange={() => setLang('de')} />
    {t('settings.language.option.de')}
  </label>
{/if}
```

Selection calls `setLang()` — immediate, no save. `document.documentElement.lang`
updates in the same tick via the `setLang` side-effect.

Not in scope:
- `src/lib/rules.ts` `describeRule()` — dead code (no call sites in
  `src/`). Skip; revisit when/if it's wired up.
- Server-returned strings (`res.json({ error: '…' })`) — stay
  English, the wrapper `t('…', { err: data.error })` pattern is
  translated around them.
- PWA manifest strings (`vite.config.ts`) — static file, stay
  English (documented limitation).
- Native `alert/confirm/prompt`: the **message text**
  (developer-controlled) is translated; the OS chrome stays OS-lang.

- `App.svelte:99` queued messages
- `App.svelte:100` failed messages
- `App.svelte:141` offline cached

- `MessageList.svelte:101` attachment(s)

### Tests

`src/__tests__/i18n.test.ts` (new file, Vitest) — 8 tests covering:

1. `t('compose.to.label')` returns the en string when `lang = 'en'`.
2. `t('some.key.only.in.de')` returns the en-fallback when
   `lang = 'de'` and the de-dict has it but en doesn't (or the
   reverse: en present, de absent → en value).
3. `t('missing.in.both')` returns the key verbatim.
4. `t('…', { name: 'Leo' })` substitutes `{name}`.
5. `tPl('app.send.success', 1)` → the one-form.
6. `tPl('app.send.success', 2)` → the other-form (with `{n}` filled).
7. `setLang('de')` changes `lang` and `document.documentElement.lang`;
   `setLang('xx')` is a no-op (type-level prevents at compile time,
   runtime guards).
8. `initialLang()` returns `'de'` when `navigator.language` is
   `'de-AT'` and no localStorage entry exists.
   (And: `initialLang()` returns the stored value when it's valid,
   or `'en'` if `localStorage` throws — two additional assertions in
   the same test file total 8–10.)

### Rollout

1. Add module + locale files (en/de dicts start empty, populated as
   we roll out) + 8 tests (RED → GREEN).
2. Translate the ~180 string sites file by file. Each commit
   re-renders cleanly in `npm run dev` and all 66 existing vitest
   tests still pass.
3. Add the Settings Language tab test: clicking `Deutsch` sets
   `document.documentElement.lang = 'de'` and the Settings heading
   re-renders as `„Einstellungen"`.
4. Gate: `npx vitest run` (66 + 9 new), `npx tsc --noEmit`,
   `npx vite build`, `node --test server` (no change).
5. Tick the ROADMAP P2 item (i18n); commit + push.

### What's left to the builder

- Key-naming polish within the `<component>.<context>.<field>` rule.
- Discover any string not in the inventory (e.g. an aria-label we
  missed) and give it the same treatment.
- If a string is genuinely dynamic and can't be keyed cleanly,
  leave it English with `// i18n-defer: <reason>` and list in the PR.

### Documented limitations (revisit when we add es/fr)

- PWA manifest + service-worker install strings stay English
  (static files, generated at build time).
- OS-native dialog chrome (close buttons, "OK"/"Cancel" labels on
  `alert`/`confirm`/`prompt`) stay OS-lang — we only control the
  message body.
- Server error bodies stay English — only the wrapper is translated.
